# P06-T08 Non-stream end-to-end report

## Result

The non-stream Chat path now has a deterministic end-to-end integration matrix through two real HTTP servers and a real PostgreSQL database. The tests assemble the same trust boundaries used by the application: request correlation, virtual-key authentication, catalog authorization, route selection, GatewayRequest/RouteAttempt recording, Adapter registry, Mock Adapter, shared upstream HTTP client, and the deterministic Mock Provider.

## Scenario matrix

| Scenario | Client result | GatewayRequest | RouteAttempt |
|---|---|---|---|
| Success | `200` logical-model completion | `succeeded/completed` | `succeeded/completed`, headers present, usage present |
| Authentication failure | `401 INVALID_API_KEY` | absent | absent |
| Unknown model | `503 MODEL_UNAVAILABLE` | `failed/model_unavailable` | absent |

Every recorded case also asserts the exact append-only Request and Attempt status-event sequence. Public responses are checked through the error envelope, while database assertions verify the richer internal category/code without comparing or persisting request content.

## Correctness issue found and fixed

The original execution table referenced `(tenant_id, logical_model)` in the mutable catalog. That made a valid authenticated request for an unknown model fail during `StartRequest` with `EXECUTION_RECORD_UNAVAILABLE`, before routing could return the intended `MODEL_UNAVAILABLE` result.

Migration `000008_allow_unknown_gateway_logical_model` removes that foreign key. A GatewayRequest is an immutable fact about client input; catalog authorization and availability are routing decisions. Tenant, project, and virtual-key compound foreign keys remain enforced. The development-only down migration can restore the catalog key after unknown-model request fixtures or historical rows have been removed; production continues to prefer corrective forward migration.
