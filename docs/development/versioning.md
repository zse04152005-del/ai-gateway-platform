# 版本与兼容性策略

## 1. 发布版本

- 正式稳定前使用 `0.y.z`。
- `z`：向后兼容修复。
- `y`：新增能力或可能需要迁移的行为变化；在 `0.x` 阶段仍需清晰记录破坏性变化。
- 达到 P1 发布门禁并稳定后再评估 `1.0.0`。

## 2. API

- HTTP 路径使用 `/v1`。
- 向响应新增可选字段通常视为兼容；删除、改名或改变语义属于破坏性变化。
- 未支持字段若影响结果或费用，应返回明确错误，不静默忽略。

## 3. 事件

- 所有事件包含 `schemaVersion`。
- 消费者遵循 tolerant reader，只读取所需字段。
- 删除字段采用“新增替代字段 → 双写 → 迁移消费者 → 停止旧字段”的流程。

## 4. 数据库

- 使用 expand/migrate/contract。
- 部署新代码前先增加兼容 Schema；旧代码退出后才能删除旧字段。
- 已发布迁移不修改内容，只能追加新迁移。

## 5. 配置与价格

- 路由策略、能力、价格和内容规则均生成不可变发布版本。
- 请求记录使用执行时的版本，历史结果不随最新配置变化。

## 6. Changelog

每次发布在 `CHANGELOG.md` 的 Added、Changed、Deprecated、Removed、Fixed 和 Security 分类中记录用户可见变化。
