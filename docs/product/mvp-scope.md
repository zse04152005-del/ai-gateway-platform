# MVP 范围与用户故事

> 状态：Accepted  
> 日期：2026-07-30  
> 对应阶段：P01-T01

## 1. 产品陈述

面向需要统一接入多个大模型的企业研发团队，本项目提供一个可自托管的 AI 网关。与普通兼容代理相比，MVP 把以下正确性作为首要目标：

1. 流式请求即使部分失败、取消或发生多次上游尝试，也能准确记录状态与费用。
2. 并发请求通过预算预留而不是事后累计，硬预算不能被绕过。
3. Provider Adapter 通过统一 Fixture 验证协议和计量语义。
4. 每次路由决策可以解释当时的候选、过滤原因和配置版本。

## 2. 目标用户

### 2.1 平台管理员

负责接入供应商、管理逻辑模型、物理部署、价格、平台级策略和系统容量。

### 2.2 租户管理员/项目负责人

负责创建项目、虚拟 API Key、模型白名单、限流、预算和查看项目用量。

### 2.3 应用开发者

通过 OpenAI-compatible API 调用模型，希望替换 Base URL 后即可运行，并获得统一错误、流式行为和 requestId。

### 2.4 审计与成本人员

查看请求、Attempt、Token 类型、价格版本和费用分录，但默认无权查看 Prompt/Response 明文。

## 3. MVP 用户旅程

1. 平台管理员注册一个 Mock Provider 和一个真实 Provider。
2. 管理员创建逻辑模型 `general-chat`，绑定两个物理 Deployment 和价格版本。
3. 租户管理员创建项目，配置模型白名单、RPM/TPM/并发数和月预算。
4. 租户管理员创建虚拟 Key；明文只展示一次。
5. 开发者使用兼容客户端调用普通或流式 Chat API。
6. 网关认证、预留预算、选择 Deployment、代理请求并记录 Attempt。
7. Provider 首包前失败时可以切换；首包后失败返回部分失败，不拼接另一个模型输出。
8. Metering Worker 幂等写入 Usage Ledger，并完成预算结算。
9. 管理员通过 requestId 查看路由、每次 Attempt 和费用分录。

## 4. P0 用户故事与验收

### US-001 创建与管理虚拟 Key

作为项目负责人，我希望创建有模型范围、有效期和配额的虚拟 Key，使应用不接触供应商真实 Key。

验收：

- 明文仅创建时返回一次，数据库只存强哈希与前缀。
- Key 可禁用、过期和轮换。
- Key 只能访问绑定租户/项目与允许模型。
- 管理接口和日志不返回明文。

### US-002 统一非流式 Chat

作为开发者，我希望使用 `/v1/chat/completions` 调用逻辑模型，并获得统一响应和错误。

验收：

- 支持 MVP 字段集合，未知且影响语义的字段返回明确错误。
- 生成全局唯一 requestId。
- 至少有 Mock 与一个真实 Adapter。
- 每次上游调用生成独立 RouteAttempt。

### US-003 可靠 SSE 流式调用

作为开发者，我希望流式输出可及时转发，取消请求后不会继续无界消耗资源或费用。

验收：

- 正确处理 SSE 分块、Flush、`[DONE]`、异常 Chunk 和断流。
- 客户端取消传播到上游，并测量释放时间。
- 有界缓冲与写超时保护慢客户端。
- 首包后不透明切换模型。
- 部分失败仍写 Attempt 与已知/估算 Usage。

### US-004 路由与故障切换

作为平台管理员，我希望配置固定、优先级或加权路由，并在主 Deployment 首包前失败时切换备用。

验收：

- 候选按租户白名单、能力、区域、状态、健康、预算过滤。
- 重试具有总 Attempt 与总时间上限。
- 每次决策保存候选、过滤原因、策略版本和最终选择。
- 已输出内容后不拼接备用模型。

### US-005 多级限流

作为租户管理员，我希望按租户、项目、Key 和模型限制 RPM、TPM 与并发，避免单个应用占满容量。

验收：

- Redis 原子限流在并发场景下符合策略。
- 失败、取消和进程异常后并发槽位能够释放或过期。
- 限流错误包含 retryable 和重试时间信息。

### US-006 硬预算预留与结算

作为项目负责人，我希望并发请求不能在余额检查后同时突破硬预算。

验收：

- 请求前按输入和最大输出估算原子预留。
- 完成后按所有 Attempt 实际费用结算并释放差额。
- 100 个并发请求测试不能突破硬上限。
- 异常预留可由 Reaper 回收并审计。

### US-007 可追溯用量账本

作为成本人员，我希望查看每个 Attempt 的输入、输出、缓存和推理 Token 及对应价格版本。

验收：

- Usage Ledger 追加写入，不覆盖历史。
- 相同事件重复消费不重复计费。
- Provider、estimated、reconciled、adjustment 来源可区分。
- 多 Attempt 成本全部计入请求总成本。

### US-008 配置发布与容错

作为平台管理员，我希望路由、模型和价格采用版本发布，控制面短时不可用时数据面继续使用最近有效配置。

验收：

- 草稿不影响生产，发布版本不可变且可回滚。
- 数据面热路径不查询控制面数据库。
- 配置包含版本与校验和，实例落后可告警。

### US-009 默认隐私保护

作为安全人员，我希望系统默认不保存 Prompt/Response 明文，并防止密钥、正文进入日志和 Trace。

验收：

- 默认只保存长度、摘要和计量信息。
- 日志、Trace、Metric Label、错误响应和审计都经过统一脱敏。
- 跨租户读取、缓存和管理 API 越权测试通过。

### US-010 可观测与可运维

作为运维人员，我希望通过指标、Trace、日志和 Runbook 定位 Provider、流式、预算、计量和配置问题。

验收：

- request、route、attempt 与 usage_publish Span 可关联。
- 有请求、TTFT、活跃流、回退、熔断、预算、计量积压和配置版本指标。
- 关键告警和 Runbook 完整。

## 5. P1 范围

- 精确缓存与安全失效。
- ClickHouse 分析报表。
- 供应商账单导入和差异对账。
- 离线评测、Shadow、质量门禁和可解释评分路由。
- 模型生命周期、策略灰度和区域/数据驻留。
- Kubernetes/Helm 与完整发布报告。

## 6. P2 范围

- MCP Server/Tool 注册、OAuth、工具级权限、审批、幂等和预算。
- Agent/A2A 最大步骤、总费用、循环检测和熔断。
- 语义缓存与租户内向量检索。
- 自托管模型的 KV Cache、LoRA、队列与 GPU 感知路由。
- 多模态、音频、图像与 Batch 计量。

## 7. MVP 明确不做

- 不适配大量供应商；只做两个以保证契约深度。
- 不训练、微调或托管模型。
- 不实现自动在线调权。
- 不执行真实 MCP 工具。
- 不实现复杂商业计费、充值和支付。
- 不保存或展示完整 Prompt/Response，除非后续明确设计留存策略。
- 不承诺外部供应商调用 exactly-once。
- 不为了“微服务”拆分大量独立服务。

## 8. MVP 完成定义

- P00～P13 所有阶段门禁通过。
- Mock 场景可在无外网、无真实 Key 环境重复运行。
- 有普通、流式、取消、断流、429、5xx、缓存 Token 和预算并发自动化测试。
- 有 Docker Compose、OpenAPI、架构文档、Dashboard、Runbook 和验收报告。
- 所有性能数字可追溯到脚本、环境、版本和原始结果摘要。
